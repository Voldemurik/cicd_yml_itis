# Памятка: команды и возможности GitVerse CI/CD

Это справочник для практики, **не готовый `student.yml`**. Ищите нужные примеры, адаптируйте их к собственному `TASK.md`, проверяйте ошибки в логах.

## 1. Git: ветки, коммиты, отправка изменений

| Задача | Команда |
|---|---|
| Клонировать форк | `git clone <URL_ВАШЕГО_ФОРКА>` |
| Посмотреть текущую ветку | `git branch --show-current` |
| Посмотреть изменения | `git status` |
| Создать и переключиться на ветку | `git switch -c student/<логин>` |
| Отправить новую ветку на сервер | `git push -u origin student/<логин>` |
| Получить последние коммиты | `git pull --ff-only` |
| Добавить изменённые файлы | `git add .gitverse/workflows/student.yml app/core.py` |
| Сделать коммит | `git commit -m "Fix quality and tests"` |
| Отправить исправления | `git push` |
| Посмотреть последние коммиты | `git log --oneline -6` |
| Посмотреть конкретные изменения | `git diff` |

Можно создать ветку в веб-интерфейсе GitVerse. **Для выдачи задания важно создание ветки `student/<логин>` на сервере**: только тогда сработает `on: create`. Если вы сделали ветку локально, её нужно отправить через `git push`.

Не создавайте ветку с именем `master` и не удаляйте свою рабочую ветку после начала практики.

## 2. Локальная подготовка Python

Работайте из корня репозитория. В Windows можно использовать PowerShell, в Linux — терминал Bash.

```bash
python --version
python -m pip install -r requirements-dev.txt
python -m pytest -q
python -m ruff check app tests
python -m ruff format --check app tests
```

`ruff check` проверяет часть правил качества; `ruff format --check` проверяет форматирование, **не исправляя файл**. Для автоматической корректировки форматирования: `python -m ruff format app tests` (после этого изучите `git diff`). Для части простых правил можно попробовать `python -m ruff check --fix app tests`.

В стартере исходные ошибки намеренные: красные результаты в начале нормальны.

## 3. Как устроен YAML

- `name:` — отображаемое имя workflow или шага.
- `on:` — событие запуска: `create`, `push`, `workflow_dispatch` или `workflow_call`.
- `jobs:` — отдельные задачи (на собственных раннерах).
- `runs-on:` — среда выполнения, например `ubuntu-latest`.
- `steps:` — последовательные действия одной job.
- `uses:` — готовое действие, например `actions/checkout@v4`.
- `run:` — команда терминала (проверяется её **код завершения**).
- `env:` — переменные окружения workflow, job или отдельного шага.
- `needs:` — запуск job **после** успешного выполнения другой job.
- `with:` — параметры действия `uses`.
- `if:` — условие запуска.

Мини-пример команды в шаге (не решение практики):

```yaml
- name: Show Python version
  run: python --version
```

YAML чувствителен к пробелам: используйте одинаковые отступы, не табуляцию. Длинную группу команд удобно оформлять через `run: |`.

## 4. Коды завершения и диагностика ошибок

Успешная команда возвращает **exit code 0**. При нарушении требования проверка должна завершаться **ненулевым кодом**. Команда `echo "OK"` лишь печатает текст; она не доказывает, что программа или тесты прошли.

Полезные команды Bash:

```bash
pwd                   # рабочая папка
ls -la                # файлы и папки
test -f README.md     # есть ли файл (возвращает код 0 или 1)
grep -Fq 'example' README.md   # существует ли строка (только пример)
mkdir -p dist         # создать каталог для результатов
cat README.md         # посмотреть текст файла
```

Опции: `grep -F` — буквальный текст, `-q` — без печати результата, `-x` — совпадение строки целиком. Команды `grep`, `test`, `ls` относятся к Linux/Bash. В PowerShell и CMD команды могут отличаться; среда `ubuntu-latest` работает с Linux.

Если CI упал, откройте **CI/CD → нужный запуск → красная job → шаг**, найдите первую реальную ошибку и её exit code. Частые причины: неверный путь, файл не создан, отсутствует зависимость, синтаксис YAML, неправильно заданный `env`.

### Дополнительные команды Bash (в `ubuntu-latest`)

| Команда | Для чего | Примечание |
|---|---|---|
| `wc -l FILE` | Число строк | Не всегда равно числу записей CSV (учтите заголовок) |
| `head -n 5 FILE` | Первые 5 строк | Удобно для быстрого просмотра |
| `tail -n 5 FILE` | Последние 5 строк | Удобно для диагностики |
| `find docs -type f` | Найти файлы | Работает в Linux |
| `sort FILE` | Отсортировать строки | Меняет только вывод |
| `sort FILE \| uniq` | Убрать соседние дубликаты | Сначала сортируем |
| `grep -n 'word' FILE` | Поиск с номерами строк | При отсутствии совпадений код выхода 1 |
| `python -m json.tool config/settings.json` | Проверить синтаксис JSON | Не проверяет бизнес-условия |
| `python -m compileall -q app` | Проверить компиляцию Python | Не заменяет тесты |
| `git diff --check` | Найти ошибки пробелов в diff | Помогает при редактировании |
| `sha256sum data/sales.csv` | Контрольная сумма файла | Для проверки идентичности входных данных |

Чтобы **проверять** условие, а не просто печатать его результат, используйте корректные коды возврата. Пример для выдуманного файла:

```bash
if test -s output/example.txt; then
  echo "File exists and is not empty"
else
  echo "Expected output/example.txt is missing or empty" >&2
  exit 1
fi
```

`test -s` означает «файл существует и непустой». Это лишь демонстрация конструкции `if`; для настоящего задания выбирайте проверку по своему варианту. Не используйте `|| true`, если по условию ошибка должна останавливать CI.

## 5. JSON и CSV: правильные проверки

JSON лучше читать парсером, а не искать кусок текста: строка `"true"` и логическое `true` — разные значения.

Пример чтения **другого** JSON-файла, не решение S3:

```bash
python -c "import json; print(json.load(open('config/settings.json', encoding='utf-8')))"
```

Для Windows удобнее сохранить короткий проверяющий скрипт `.py` и запустить `python путь/к/скрипту.py`, чем писать длинную команду с кавычками.

Для CSV в Python обычно используют `csv.DictReader`, а для числовых расчётов — `int` и `Decimal`. Запуск приложения практики:

```bash
python -m app.cli --help
python -m app.cli --input data/sales.csv --output dist/demo.json --mode row_count --variant DEMO
```

Пример выше использует **демонстрационный** режим и файл `dist/demo.json`. В персональном задании могут требоваться другие режим, путь и идентификатор варианта.

## 6. Переменные окружения и параметры

Например, на уровне шага:

```yaml
- name: Example environment
  env:
    MESSAGE: "hello"
  run: echo "$MESSAGE"
```

Если переменная нужна только одному шагу, размещайте `env` именно в нём. Для всей job можно задать `env` рядом с `runs-on`.

## 7. Артефакты: сохранить и получить

`actions/upload-artifact@v4` загружает **созданный** файл из job. `actions/download-artifact@v4` скачивает его в последующей job. Поскольку jobs запускаются в отдельных средах, один и тот же локальный каталог между ними автоматически не сохраняется.

Схематичный пример с **посторонним учебным файлом**:

```yaml
- name: Upload demo artifact
  uses: actions/upload-artifact@v4
  with:
    name: example-bundle
    path: example-output.txt
    retention-days: 7
```

Во второй job нужно указать зависимость через `needs`, затем использовать `actions/download-artifact@v4` с тем же именем. В текущей практике реальные имя и путь отчёта указаны в `TASK.md`.

## 8. Частые ошибки в нашей практике

| Симптом | Что посмотреть |
|---|---|
| Workflow не появился после создания ветки | CI/CD включён? ветка на сервере? имя `student/<логин>`? |
| Генератор создал artifact, но нет `TASK.md` в ветке | Лог шага `Commit assignment`: возможно, запрещён push из CI |
| Ruff завершился с ошибкой | Лог Ruff; проверьте форматирование и синтаксис |
| Pytest красный | Какой тест не прошёл, какие ожидания и реальные значения |
| `variant_check` зелёный, а аудит красный | Формат проверки не удовлетворяет фактическому условию |
| `package` не запускается | Проверьте `needs` и предыдущие job |
| Артефакт не найден | Создан ли файл, верны ли `name`/`path`, прошёл ли upload |
| Audit красный при успешном Student CI | Посмотрите каждый пункт `teacher-audit`, правильность ветки и variant |
