# Пошаговая инструкция студенту: от eLearn до финального запуска

## 0. Что у вас уже есть

Ссылка в eLearn ведёт к **вашему** репозиторию GitVerse — форку преподавательского проекта. **Не создавайте ещё один форк** и не присылайте ссылку на исходный преподавательский репозиторий. В `master` уже лежат код, тесты, три workflow и справочная документация.

## 1. Создание студенческой ветки — выдача задания

1. Посмотрите точный логин своего аккаунта GitVerse, например `ivanov`.
2. Из `master` создайте ветку **`student/ivanov`** в своём репозитории. Можно через веб-интерфейс GitVerse (создать ветку от `master`) или локально:

   ```bash
   git switch master
   git pull --ff-only
   git switch -c student/ivanov
   git push -u origin student/ivanov
   ```

3. В `CI/CD` найдите запуск **`01 - Assign task on branch creation`**. Он должен создать **два файла прямо в вашей ветке**: `TASK.md` — понятное задание и `variant.json` — техническое описание варианта.
4. Переключитесь на свою ветку и откройте `TASK.md`. Если вы работаете локально, сначала `git pull --ff-only` — генератор успел добавить коммит в GitVerse.

**Если задания нет:** имя ветки должно точно совпадать с `student/<ваш_логин>`, и ветка должна быть создана на сервере. Не делайте повторно случайные ветки; сначала проверьте логи генератора. Не изменяйте `variant.json` вручную.

## 2. Исправление проекта и `student.yml` (YAML-часть)

Работайте **только в своей студенческой ветке**. В `.gitverse/workflows/student.yml` уже задан каркас: `quality` → `variant_check` → `package` → `audit`.

**A. Качество кода (общее для всех).** Изучите ошибки Ruff, исправьте форматирование `app/` и `tests/`; настоящий `pytest` должен проходить. В `app/core.py` есть специально внесённая вычислительная ошибка. Не отключайте тесты. Для CI используйте отдельное Python venv, чтобы системный pip на раннере не конфликтовал с PEP 668.

**B. Персональная статическая проверка.** В `TASK.md` дан код `S1`–`S6` и точное условие (текст, файл, JSON-ключ и т. п.). Добавьте в `variant_check` команду, которая **действительно проверяет условие** и возвращает ненулевой код при ошибке.

**C. Динамическая проверка.** У каждого варианта есть режим `D1`–`D6`. В `package` укажите через `env` переменную `REPORT_MODE`, затем запустите `python -m app.cli` на `data/sales.csv`, передав параметры `--input`, `--output dist/report.json`, `--mode "$REPORT_MODE"`, `--variant` из `TASK.md`.

**D. Артефакт.** Загрузите `dist/report.json` через `actions/upload-artifact@v4` с именем **`student-results`**. Следующая job `audit` автоматически скачает именно этот артефакт и проверит содержимое. Секцию `audit` не меняйте.

Делайте небольшие коммиты. CI запускается на каждый push в `student/**`; при необходимости он доступен вручную через `workflow_dispatch`. Красный результат — повод посмотреть **первую содержательную ошибку в логах**, а не переписать всё сразу.

## 3. Как понять, что YAML-часть выполнена

В `CI/CD` должен быть успешный запуск **`02 - Student CI + artifact audit`** для вашей ветки. В нём прошли `quality`, `variant_check`, `package`, `audit`; в `audit` написано **`RESULT: PASS`**, а среди артефактов есть `student-results` (и, возможно, `teacher-audit`).

**Скопируйте ID этого запуска:** в адресной строке GitVerse это номер после `/cicd/`, например в `.../cicd/1234567?job=987654` нужен **`1234567`**, а не `987654`.

## 4. Работа с секретами — отдельная часть

Следующий этап **не требует изменения `student.yml`**. По документу [READ_TOKEN.md](READ_TOKEN.md) создайте личный токен GitVerse с правом **чтения репозитория** и добавьте его в свой репозиторий: **Настройки → Секреты и переменные → Секрет `READ_TOKEN`**. Не используйте обычную переменную и не записывайте сам токен в файлы.

Секрет нужен готовому `smartclass.yml`, который обращается к API GitVerse. Студенту не надо писать HTTP-запрос или исправлять преподавательский workflow.

## 5. Итоговый Smartclass

1. Откройте `CI/CD` своего репозитория.
2. Выберите **`03 - Smartclass: verify Student CI run`** → ручной запуск (**workflow_dispatch**).
3. Обязательно выберите свою ветку `student/<логин>`.
4. В поле **`student_run_id`** вставьте ID успешного запуска Student CI, скопированный на шаге 3.
5. Дождитесь окончания Smartclass. Откройте его лог: должна быть строка **`RESULT: PASS`**.

Smartclass проверит, что ID существует, относится к `student.yml`, к **вашей** ветке и успешен. Если после успешного CI вы изменяли проверяемый код, лучше ещё раз запустить Student CI и указать **новый** ID. Отличающийся SHA в Smartclass не делает проверку автоматически красной, но фиксируется как предупреждение для преподавателя.

## 6. Что сдавать

Сохраните ссылку на **свой форк** и ссылку на **успешный запуск Smartclass**. Передайте их так, как указано в eLearn. Не удаляйте студенческую ветку, артефакты и историю коммитов до окончания проверки. При необходимости создайте Pull Request в `master` после успешного Smartclass.

## 7. Если что-то не получается

| Проблема | Что делать |
| --- | --- |
| Нет `TASK.md` | Проверить имя ветки, событие `create` и лог `generate-variant.yml` |
| Ruff нашёл ошибки | `python -m ruff check ...`; `python -m ruff format ...` локально, посмотреть `git diff` |
| `pytest` упал | Исправить исходный код, не тесты |
| `audit` не нашёл отчёт | Убедиться, что job `package` успешна, файл `dist/report.json` существует, артефакт называется `student-results` |
| `externally-managed-environment` | Используйте venv, не `--break-system-packages` |
| Smartclass сообщает `Missing READ_TOKEN` | Секрет не создан или создан как обычная переменная |
| Smartclass сообщает `HTTP 401/403` | У токена нет доступа или он неверен |
| Smartclass сообщает `Run belongs to another branch` | Вручную запускать на той же ветке, где был Student CI |
| Ошибка `Requested run is not Student CI` | Указан ID неправильного workflow / отдельной job |

Подробные примеры команд: [CI_CHEATSHEET.md](CI_CHEATSHEET.md). Никогда не публикуйте токены в сообщениях преподавателю.
